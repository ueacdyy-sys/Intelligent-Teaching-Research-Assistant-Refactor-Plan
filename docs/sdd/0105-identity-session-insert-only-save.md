# SDD 0105: Identity Session Insert-Only Save

## Problem

SDD 0104 showed that the remaining 4400-concurrency Identity tail is not lock
contention and should not be addressed by blindly raising connection limits.
The next safe write-path target is the login and grant session insert.

`SaveSession` currently uses `INSERT ... ON CONFLICT (session_id) DO UPDATE`.
All production session IDs are generated by the token issuer from 24 random
bytes. Treating that generated ID as an upsert key makes the hot path pay for a
conflict-update branch that should never be a normal business path. If a
session ID collision ever happens, overwriting an existing session is also the
wrong safety behavior.

## Source Requirement References

- Root requirement: teacher, student, and remote entry points need a stable
  shared identity boundary.
- Root requirement: packaging and runtime must stay compact, stable, and
  efficient.
- Root requirement: local performance secrets use `ueacd`.
- SDD 0099: redundant active token indexes were removed to reduce session table
  write amplification.
- SDD 0102: scalar timestamp columns became authoritative to reduce refresh
  rotation write work.
- SDD 0104: PostgreSQL wait timeline evidence points to write-path pressure and
  gateway-side scheduling, not lock contention or simple PgBouncer queueing.

## Scope

In scope:

- Change PostgreSQL `SaveSession` to insert a new row only.
- Preserve the `identity_sessions.session_id` primary key as the collision
  guard.
- Fail duplicate session IDs instead of overwriting existing session state.
- Align the no-database memory fallback with the same duplicate-session
  behavior.
- Keep public Identity HTTP contracts unchanged.
- Keep access-token and refresh-token lookup behavior unchanged.

Out of scope:

- Removing token uniqueness constraints.
- Changing token or session ID generation.
- Changing refresh rotation, self-revoke, prune, or remote replay semantics.
- Raising PostgreSQL, PgBouncer, gateway pool, or ingress limits.
- Introducing Redis, caches, model dependencies, OCR, RAG, vectors, embeddings,
  or training dependencies.

## Contracts Touched

- PostgreSQL `SaveSession` issues a plain insert into `identity_sessions`.
- The insert SQL must not contain `ON CONFLICT`.
- A duplicate `session_id` is an error and must not replace the existing row.
- The memory fallback session store must also reject duplicate generated
  `session_id` values.
- Existing access and refresh token reads still resolve the original principal.
- Public Identity HTTP response shapes and status semantics are unchanged for
  normal generated sessions.

## Acceptance Criteria

- A focused PostgreSQL adapter test fails before implementation because
  `SaveSession` still contains `ON CONFLICT`.
- A focused PostgreSQL adapter test proves duplicate session IDs are rejected
  and the original token mapping remains intact.
- A use-case test proves duplicate generated session IDs are rejected without
  replacing the original memory fallback session.
- `go test ./services/identity-access-gateway/internal/adapter/postgres -count=1`
  passes.
- `go test ./services/identity-access-gateway/... -count=1` passes.
- `npm run audit:performance-evidence` remains READY.
- `npm run quality` passes.
- A follow-up 4400 logical-concurrency benchmark compares this insert-only
  write path with the SDD 0104 baseline.

## Rollback Plan

Restore the previous `ON CONFLICT (session_id) DO UPDATE` clause in
`SaveSession` and restore the fake PostgreSQL adapter test double overwrite
behavior. SDD 0104 remains the current performance evidence if the insert-only
save path is rolled back.
