shape and PgBouncer 180 runtime.

## Failure Source

All workload errors came from `conversation_write`. The first error was:

```text
Post "http://127.0.0.1:18409/v1/research/conversations": dial tcp 127.0.0.1:18409: connectex: No connection could be made because the target machine actively refused it.
```

Conversation timing did not indicate database saturation:

```text
conversation_write p99 latency: 985.05ms
server timing p99: 117.18ms
db.acquire p99: 0ms
db.batch_wait p99: 72.68ms
db.insert p99: 70.02ms
client/server gap p99: 971.57ms
```

All 16 conversation workers were reachable in the post-run runtime diagnostics,
so the failure is best read as a high connection-surge/listener availability
edge, not as a persistent worker crash. That is an inference from the current
evidence, not a proven root cause.

## Interpretation

Under this exact transport profile, the current practical mixed-load boundary
is between `mixed4400` and `mixed5800`.

This is not a PostgreSQL/PgBouncer capacity failure. The hot-path pool sum
remained 137 under a PgBouncer cap of 180. The failed module was conversation,
and the error shape points toward connection surge or worker listener
availability. Identity remains the latency bottleneck but did not fail.

## Next Step

Run a tuned `mixed5800` retry with a lower conversation client connection surge
while keeping Identity overrides unchanged. If that passes, the limit is
transport/listener configuration rather than application logic capacity. If it
still fails, collect deeper conversation runtime diagnostics around refused
connections.
